# Build a jam feature

Orchestration order for one feature. Don't skip steps; each one is cheap and catches the next step's failure early.

## 1. Scope it (no tools beyond grep)

- `grep -n "^## " "Assets/GameJam/Don't Let the Balloon Drop Game Design Document.md"`, then read only the matching section.
- Check the feature against the GDD scope list: must / should / stretch. If a must-have is unfinished and this is should/stretch, say so and ask before continuing.
- Write a 3 to 6 line plan in chat: scripts (with asmdef), config fields, prefab, how to verify. Ask one question only if a design rule is genuinely unclear.

## 2. Config first

Extend an existing ScriptableObject in `Scripts/Core/Config/` before adding a new one. Existing:
`BalloonConfig`, `SlapConfig`, `RunConfig` (timer, score, medals), `PlayerRigConfig`, `KnockbackConfig`, and
one `ItemDefinition` per item (`Config/Items/Item_*.asset`). Every tunable number goes there, defaulting to
the GDD's starting values, with `[Tooltip]` text citing the GDD rule. Config fields are public PascalCase.
A new config type gets a property in `Scripts/Editor/PrototypeConfigSet.cs` so the builder creates its asset
under `Assets/GameJam/Config/` (created once, never overwritten, so tuning survives rebuilds).

## 3. Code

- Put the script in the asmdef that owns it (see CLAUDE.md §3); reference other assemblies, never `Assembly-CSharp`.
  Dependency direction is fixed: Core ← Gameplay ← Player ← Net ← Editor. Gameplay and Player never
  reference Fusion; they talk to networked objects through `GameJam.Core` interfaces (`ISlappable`, `IGrabbable`,
  `IRunStatus`, `IKnockbackRelay`, `ISpikeSurface`) and `GameServices`.
- Naming: namespaces `GameJam.<Assembly>`, `[SerializeField] private` fields named `_camelCase`, PascalCase
  properties and methods, `sealed` components, braces on every `if`, one MonoBehaviour per file. Components that
  the builder wires get a `Configure(...)` method instead of public fields.
- New course pieces (hazards, pads, gates) are local `MonoBehaviour`s in `Scripts/Gameplay/Course/` that
  `BalloonPhysics` and `RigHazardSensor` detect with `GetComponentInParent`. Time anything rhythmic with
  `CourseClock.Time` so every headset agrees without network traffic.
- Gameplay logic in plain C# or a local MonoBehaviour first; networking goes in a separate `NetworkBehaviour` wrapper (load `fusion-networked`). This keeps Day 1 solo testing possible.
- No per-frame allocations (no LINQ, `GetComponent`, `new` lists or string concatenation in Update/FixedUpdate). Cache references in `Awake`.
- Physics in `FixedUpdate`. Slap and hit detection use tracked hand velocity, not collider contact alone (GDD: The balloon / Movement).
- Expose events (`public event Action<...>`) for audio, haptics, commentator and UI to hook later, so polish never edits core logic.
- `unity recompile` after each file group (see `unity-cli-loop` §1).

## 4. Prefab and scene

The placeholder prototype is generated by code in `Scripts/Editor/`: `PrototypeSceneBuilder` (entry, rig,
network), `PlaceholderPrefabBuilder` (networked prefabs in `Prefabs/Net/`), `BackyardCourseBuilder` (the open yard: zones, hoops, movers, in
the scene). Add the feature's prefab or course piece there, then rebuild:
`unity command script eval ... -- --code 'return GameJam.Editor.PrototypeSceneBuilder.BuildFromCli();'`
It refuses to run over unsaved scene changes, regenerates `Scenes/Prototype.unity`, the prefabs and the
placeholder materials, and rebuilds Fusion's prefab table. Hand-made changes to generated prefabs are lost,
so put them in the builder. One-off edits to other scenes still use a snippet (`unity-cli-loop` §2).
Placeholder art is primitives with URP Lit materials from `Materials/Placeholder/`; tint at runtime with a
`MaterialPropertyBlock` on `_BaseColor`, never `renderer.material` (it leaks a material per call).

## 5. Verify

`unity-cli-loop` §3: play, confirm frames advance, read errors, and check the feature with one
`script eval` that returns its state (e.g. balloon velocity after a simulated slap, last-hitter id,
pop count). Useful hooks: `GameJam.Core.GameServices.Run.RequestStart()`, `GameJam.Net.GameState.Instance`
(`State`, `HoopsCleared`, `HoopCount`, `CurrentCheckpoint`, `Pops`, `LastScore`, `WristText`), `GameJam.Net.NetworkBalloon.Instance.RequestHit(player, velocity)`,
and teleporting the balloon (`NetworkTransform.Teleport`) onto a `Sharp`, a `HoopN` object, the lawn (ground pop) or the `FinishLine`. Without a Fusion App ID the game runs
offline in Single mode, which covers everything except multiplayer. State plainly what was verified in the Editor and what needs a headset or a second player.

## 6. Hand off

Two or three sentences: what was built, where (files, prefab), the tuning values to try in the
next playtest, and anything left for the headset. Offer a commit; don't commit unasked.
